# A shared selection action bar, lifted into the top layer

## Status

accepted

## Context

Event storming's board had its own floating bar for when the reader selected more than one slice or link: a count, a primary action ("コンテキストにまとめる" / group into context), an "add to an existing context" select, "remove from context", "delete" and a close button, anchored to the bottom of the canvas. It was built entirely out of the template's own markup and CSS (`.board-selection` in `src/templates/event-storming/styles.ts`), positioned `absolute` inside `.board-viewport` — a pan/zoom surface with `overflow: hidden` for its own reasons (clipping content that scrolls past its edges). The bar happened to still fit inside that viewport's bounds, but nothing guaranteed it would keep fitting, and nothing about the pattern was reusable: a second board (whiteboard's selection toolbar, `src/templates/whiteboard/render/toolbar.ts`) ended up with its own, differently-shaped bar instead of sharing one.

A multi-selection action bar is not specific to event storming, or to templates at all: anything that can hold a selection — a template's own board, or a diagram component rendering its own nodes — needs the same three things: show what is selected, offer actions on it, and clear it. That is a shell concern (chrome, placement, keyboard), not a per-board one, the same reasoning that moved grill's questions into the shared shell (`20261016_grill-in-core.md`). Unlike grill, this does not need a new action vocabulary or base-data shape; it is a UI contract only, so it belongs beside the other public custom elements in `src/components/*`, not inside `TemplateElement` — a board can be a template's shadow root today and a diagram component's shadow root tomorrow (`20261020_multi-board-pages.md` already separates boards from the template base; a host does not have to be a template at all).

Two problems specific to this UI had to be solved regardless of where the code lives:

- **Clipping.** A board that legitimately wants `overflow: hidden` (so panned/zoomed content does not spill out) cannot also host a `position: absolute` bar and guarantee it stays visible — the two needs conflict structurally, not by oversight.
- **At most one bar on screen.** A page can have more than one board or diagram component, each with its own selection. Only the most recently focused one should show a bar; an older selection does not disappear, it just stops being the one with a visible bar.

## Decision

`<dpk-selection-bar>` (`src/components/selection-bar/`) is a content-free chrome element: it renders nothing itself (no label text, no buttons) beyond a `role="toolbar"` surface and a default slot. The host places it anywhere in its own light DOM (conditionally, exactly like any other piece of markup it already renders) and slots in whatever it already had — a count `<span>`, its action buttons, its own `<select>`, its own close button. Slotted content keeps its existing styling (shadow DOM styles content from its origin tree, not the receiving host's), so migrating a bar is a pure structural wrap: no button, text or event-handler wiring inside the bar changes.

- **Escaping clipping: the Popover API, not a core-owned DOM portal.** The bar's surface carries `popover="manual"`, permanently. Showing/hiding it (`showPopover()` / `hidePopover()`, driven by whether the element is connected) promotes it to the top layer for painting without moving it in the DOM tree — it stays exactly where the host placed it, so event bubbling, slotting and inherited CSS custom properties all keep working normally; only paint order and clipping are affected. This is why no ancestor's `overflow: hidden` (`.board-viewport`'s, in event storming's case) can clip it, without a core-owned portal element the host would have to render into. `manual` mode (not `auto`) is deliberate: `auto` would auto-dismiss the bar on an outside click or on a second popover opening, firing the same native dismiss regardless of _why_ — indistinguishable from the page's own selection being cleared versus the bar simply being pre-empted by another one, which would wrongly suggest to the host that its selection should clear too. `popover="manual"` makes dismissal entirely the component's own `#open` state, driven only by connection and the coordinator below — never by the UA's own heuristics. This is a different mechanism from the pre-existing `PopoverController` / `openPopover` (`src/core/popover-controller.ts`) used for anchored dropdown positioning (combobox's listbox, say); the two are unrelated despite the name, and `dpk-selection-bar` does not use `PopoverController`.
- **At most one bar shown: an explicit core-owned coordinator, not reliance on native auto-dismiss.** `src/components/selection-bar/coordinator.ts` keeps a single module-level "current claim". Connecting a `<dpk-selection-bar>` claims it (hiding whoever held it before — hidden, not cleared: the pre-empted claimant's own selection is untouched, only its bar steps aside); disconnecting releases it. The most recently _mounted_ bar wins, which in practice means the most recently focused/active board, since a host only renders its bar while it has a non-empty selection.
- **Chrome lives in `core/theme.ts`, not `components/atoms/*`.** A new atom, `.dpk-floatbar` (next to `.dpk-btn`, `.dpk-select`, etc. in the `controls` CSS module already included by every shadow-root component), supplies the visual surface — border, background, blur, shadow, the lift-in animation. `src/components/atoms/*` is a separate, `document`-level system for author-owned light-DOM markup (`.dpk-count`, `.dpk-filter`, …); `.dpk-floatbar` is for a shadow root's own template, the same category `.dpk-btn` is in, so it lives alongside it.
- **Placement is the component's own, not the template's.** `<dpk-selection-bar>`'s own styles fix bottom-center, clear of the hand-off dock (`--dpk-dock-clearance`) — the one placement core imposes, chosen because it matches where every migrated bar already sat. A host that needs a different spot claims the bar from a different place in its own markup instead of overriding this from outside; nothing about the contract requires bottom-center, only the current component ships that choice.
- **Escape.** `Escape` while focus is inside the bar fires `dpk-selection-clear` (bubbles, composed); the host decides what that means (normally clearing its selection, which then stops rendering the bar, which disconnects it and releases the claim). No `stopPropagation()` is needed: event storming's own board-level Escape handler only reacts when the event's target is the board viewport itself, not a bubbled descendant, so the two handlers cannot double-fire.
- **No new text anywhere.** The bar's only property, `label`, is used solely as the toolbar's `aria-label` (not rendered visually); core renders no button, count or hint of its own, so there is nothing for it to need new copy for. Event storming's migration reuses its existing `messages.ts` strings verbatim.

Event storming is migrated: `renderSelectionBar` (`src/templates/event-storming/render/board.ts`) now wraps its unchanged inner markup in `<dpk-selection-bar>` instead of a plain `<div class="board-selection">`; `styles.ts` keeps only the slotted text rules (`.board-selection-count`, `.board-selection-hint`) and drops the outer chrome, now `.dpk-floatbar`'s.

Whiteboard's selection toolbar (`renderSelectionToolbar`, `src/templates/whiteboard/render/toolbar.ts`) is **not** migrated: it anchors itself above the live selection's bounding box (`anchorOf`) and carries per-item-type tool groups (color, text size, stacking, connector endpoints) rather than a fixed count-and-actions shape. Forcing it into the fixed bottom-center placement this component ships would be a behavior change, not a pure wrap, so it is left as-is and listed here for a future, more deliberate pass if a second anchored variant is ever justified. No other template or component (task-board, kanban, usm, delegation-poker, example-mapping, prototype, slides) has a comparable multi-selection action bar; kanban's `is-selected` styling is single-item, not a selection with its own action bar.

## Consequences

- **New public element.** `<dpk-selection-bar>` (`src/components/selection-bar/index.ts`, `defineSelectionBar()`) joins `registerAtoms()`, so every entry that already calls `registerComponentElements()` picks it up for free; event storming's own standalone entry (`src/entries/event-storming.ts`) registers it explicitly, as it does for every element it renders.
- **A board or diagram component anywhere can adopt the same bar** by wrapping its existing selection markup, with no change to the markup itself — the contract does not depend on `TemplateElement` or any template-specific base.
- **One bar at a time, globally**, is now an explicit, testable rule (`src/components/selection-bar/coordinator.test.ts`) instead of an accident of there only having been one board with a bar before.
- **A second anchored-to-selection pattern (whiteboard's) remains unaddressed** by this change; revisiting it means either accepting a second, differently-shaped component or extending this one's placement contract, not forcing today's fixed bottom-center shape onto it.
