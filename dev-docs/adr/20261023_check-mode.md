# Check Mode: a reader-only tally over the existing review-target marker

## Status

accepted

## Context

A long review session loses track of what has already been looked over, especially on a page with many small items (a board's cards, an ER diagram's tables) and across several sittings. The reader wants to mark items off as they go, see at a glance what is left, and be warned when an item they already checked has since changed underneath them. None of this is a judgment about the content — it carries no opinion for the agent to read, unlike a comment or an answered question — so it must never enter the draft (`src/core/action.ts` / `serializeDraft`) or the hand-off brief; it is purely something the reader keeps for themselves, the same way the change notices' "seen" record is reader-only (`20261013_change-notices.md`).

Two design questions follow from that:

- **What counts as a "main target element"**, and how does a template or component say so, without inventing a second attribute parallel to one that already exists for a near-identical purpose? The change log (`src/core/changes.ts`) already lets an author point a change at `data-dpk-target="type:id"` (`TARGET_ATTRIBUTE`, `src/core/shell/reveal.ts`), and most templates already stamp their cards with it so "Show" can scroll to them (task-board's todos/records/questions, USM's board/overviews/burndown, event storming's notes, whiteboard's board, example mapping's board, delegation poker's board, slides' stages, prototype's stage). Diagram-family components (ER diagram, sequence/state diagrams, dependency graph, architecture map, mind map — everything built on `src/components/diagram/element.ts`) mark comment targets through a parallel `data-comment-kind`/`data-comment-id` + `commentTargets()`/`commentRef()` mechanism, because those components render into their own virtual/canvas coordinate space rather than one DOM node per item; each already computes a stable per-node ref string through `commentRef(kind, id)` for that purpose, so Check Mode reuses that exact string as the node's `data-dpk-target` instead of deriving a second one.
- **How a checked mark is told apart from a stale one.** The reader has no way to know an item changed unless Check Mode is told about changes somehow — reinventing that detection (diffing state, watching mutations) would duplicate the change log's entire job.

## Decision

Check Mode reuses `data-dpk-target` as its authoring contract, rather than adding a new attribute: anything already marked for the change log's "Show" is, for free, a Check Mode target. `src/core/shell/check-mode-badges.ts`'s `collectCheckBindings` walks the DOM the same way `reveal.ts` does (`queryAllDeep`, through nested shadow roots) and finds every `[data-dpk-target]` element. This means templates needed no changes to pick up default coverage. Diagram-family components stamp their main per-item node (a table, a state, a participant, a service, a module) with `data-dpk-target=${this.commentRef(kind, id)}` alongside the existing `data-grill-questions`, deliberately scoped to that node-level granularity — not ER columns, not diagram edges/labels, not sequence messages — matching how templates already mark card-level items rather than every sub-field. Because `queryAllDeep` has no depth limit, this requires no change to `collectCheckBindings` itself, and it works the same whether the diagram is embedded directly in a template or hosted as a board of `<dpk-page>` (`20261023_diagram-as-board.md`): the page's own `renderChrome` (inherited by `PageElement` from `TemplateElement`, never overridden) already collects and badges across every board's shadow root, so a multi-board page needed no `src/core/page/**` changes either.

Staleness is derived from the change log instead of tracked separately. A checked mark records the change log's current revision at the moment it was checked (`src/core/check-mode.ts`'s `CheckRecord.revision`); `statusOf` then asks whether any revision _after_ that one carries a change whose `target` matches the same ref (`revisionsOf`, already used by the notices themselves). If so, the mark reads `'stale'` ("(?)") instead of `'checked'`. A page with no change log at all treats every checked mark as simply `'checked'` forever — there is nothing to compare against. One click on a `'stale'` badge re-affirms it as checked at the now-current revision, rather than requiring an uncheck-then-recheck round trip; only a `'checked'` badge's click removes the mark.

State and its storage are a new, parallel pure model (`src/core/check-mode.ts`'s `CheckState`/`withEnabled`/`withToggled`/`statusOf`, persisted by `src/core/shell/check-mode-controller.ts`'s `CheckModeController`) rather than a field inside the change notices' own `SeenRecord`: Check Mode has its own lifecycle (a reader can turn it on and off, which the seen record has no equivalent of) and its own key, `` `${storageKey}:check-mode` ``, through the same `JsonStore` the seen record and unsent-text recovery already use (`src/lib/dom/json-store.ts`) — guaranteeing it stays out of `src/core/persistence.ts`'s `DraftStorage`, which is the only store the agent's hand-off ever reads from.

Turning Check Mode off clears every mark (`withEnabled(state, false)` resets to empty) because a stale "(?)" would otherwise accumulate meaninglessly across sessions where the reader is not even using the feature, and because re-enabling with everything already checked would defeat the point. Since this is destructive, the shell asks first, with a new shared confirm prompt rather than `window.confirm` (unstylable, blocks the whole thread, and cannot be skinned to the page's own chrome): `src/core/confirm-dialog/controller.ts`'s `ConfirmDialogController`, a `ReactiveController` wrapping a native `<dialog>` shown with `showModal()`, following the same "logic in `core`, public element wraps it" split as `SelectController`/`dpk-select` (`20260924_dpk-naming.md`) — core's own shell (`element.ts`) cannot import `src/components/*` (`core-template-boundaries`), so the reusable behavior has to live in `core` for the shell to use it at all, and is then re-exposed as `<dpk-confirm-dialog>` (`src/components/confirm-dialog/`) for pages that want the same prompt. Unlike `dpk-select`, the public element's contract is imperative only (an `ask(options): Promise<boolean>` method, no declarative attributes) because a confirm prompt has no persistent state to bind — it is a single question with a single answer, and forcing a declarative open/close property onto it would only add a second way to drive the same one-shot interaction. `<form method="dialog">` with `<button type="submit" value="...">` is used throughout so the native dialog closes itself and reports which button fired via `dialog.returnValue`, instead of each caller wiring `preventDefault`/manual `close()`.

Badges are rendered the same way the grill's question badges are — an absolutely-positioned overlay per region (sidebar/main), one badge per binding, repositioned on scroll/resize/pan — so the existing DOM-measurement code (`visibleAreaOf`, corner/gutter placement math) was pulled out of `src/core/shell/grill-badges.ts` into a shared `src/core/shell/badge-dom.ts`, parameterized by a `gutterOf` predicate. Check Mode's own badges always sit at the target's corner (`gutterOf: () => false`); the grill's keep their existing author-markup-gutter-vs-diagram-overlay logic unchanged.

## Consequences

- **Zero-effort default coverage** for every template that already marks `data-dpk-target` for the change log: task-board, USM, event storming, whiteboard, example mapping, delegation poker, slides, prototype. A reader can check off cards in any of these today without the template being touched.
- **Diagram-family components are covered too**, node-level: ER diagram's tables, state diagram's states, sequence diagram's participants, architecture map's services, dependency graph's modules, mind map's topics, and kanban's cards. A diagram's edges, labels, ER columns and sequence messages are deliberately left unmarked, the same way a template never marks its cards' sub-fields.
- **A page's multi-board header (`<dpk-page>`) gets Check Mode for free too**, since `PageElement` never overrides `renderChrome` — it is one more `TemplateElement` instance whose own DOM happens to contain other boards as slotted children.
- **Staleness is only as precise as the change log's own `target` refs.** A change entry with no `target` (a general announcement) never marks anything stale; an author who wants Check Mode's staleness to fire accurately needs to keep targeting change entries the same way "Show" already depends on them to.
- **A second native-`<dialog>`-based component exists now** (`dpk-confirm-dialog`), alongside the page's existing `popover="manual"` overlays (selection bar, settings menu); the two mechanisms are not unified, since a confirm prompt's modal, must-answer nature is a different contract from a dismissable popover.
- **`badge-dom.ts` is a new shared layer** between the pure `badge-layout.ts` (geometry only) and each feature's own badge module (`grill-badges.ts`, `check-mode-badges.ts`); a third badge-like feature should extend it rather than re-deriving `visibleAreaOf`/positioning again.
