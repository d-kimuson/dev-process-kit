# Localize the kit's UI from the page's `lang`

Every public element renders its own text (the review rail, template chrome, diagram controls, action titles) in the language the page declares with `lang`, unless the reader picks another one in the template header. The kit ships English and Japanese; English is the default.

## Status

accepted

## Context

The kit's own text was written in Japanese, mixed with a few English words (`Copy brief`, `draft · note`). Pages are generated by an agent in the user's language, so an English-speaking user got a Japanese review rail around English content. The text lives in every layer: the core shell, the comment panel, the pure `describe` functions of every template (whose titles also reach the hand-off brief), and every diagram component.

The alternatives weighed:

- **A locale attribute of our own** (`locale="en"`). It duplicates `lang`, which HTML already defines, which assistive technology already reads, and which an agent already writes on `<html>`. It is also one more thing to forget on each element.
- **The browser's language** (`navigator.language`). A reviewer's browser says nothing about the page: a Japanese reader reviewing an English page would get a Japanese rail around English content, and the same HTML would render differently per reader.
- **Only the author decides.** A reader who does not read the page's language would be stuck with it; the choice of UI language is the reader's as much as the author's.
- **A message-override API** so a page can rename labels. It turns every message key into public contract, and the only need we know of is language, which `lang` covers.
- **An i18n library** (for example ICU MessageFormat). It adds a dependency and a runtime for plural rules we do not need; our messages are short labels with a few interpolated numbers.

## Decision

- **The locale is the closest `lang`.** An element looks at its own `lang` attribute, then its ancestors, crossing shadow roots to their hosts, and uses the first one it finds. Only the primary subtag counts (`ja-JP` is `ja`). A missing, empty or unsupported `lang` falls back to **English**. Because elements inside a template's shadow root resolve through the host, `lang` on `<html>` or on the template element reaches every nested element; the latter is what works where the author does not control `<html>` (a Claude Artifact).
- **The reader can switch it in the template header.** A language select sits beside the theme toggle and starts on the language resolved above. A pick is the reader's, not the page's: it is stored per origin under `dev-process-kit:locale`, like the color scheme, and nothing is stored with `storage="off"` or `"memory"`. Picking the page's own language clears the stored pick, so the page follows its `lang` again. The template applies a pick by writing it to its own `lang` (and restores the author's `lang` when the reader goes back), so nested elements resolve it through the same rule; a `dpk-locale-change` event on `document` tells already-connected elements to resolve again.
- **Resolved on connect and on each pick.** An author changing `lang` afterwards is not observed. Pages are generated, not switched at runtime by their author.
- **English and Japanese are bundled into every entry.** No locale loading, no network request, and a page can mix elements of both languages.
- **No public override API.** Messages are an implementation detail, like Lit.
- **Each module owns its messages.** A template or component keeps one typed dictionary per language next to its code; the compiler rejects a language that misses or adds a key. The core provides only locale resolution and the dictionary helper, and keeps its own shell text in its own dictionary. Pure presentation functions receive the dictionary (or a locale-bound template definition) as input; they never read the DOM.
- **The brief stays English where it addresses the agent.** Headings, the "How to apply" text and the comment sent to Claude are instructions for an agent and do not change. Action titles and target labels follow the page's language, since they quote what the reader saw.
- **English follows each method's canonical vocabulary** (Story / Rule / Example / Question in Example Mapping, Bounded Context in Event Storming, Activity / Step / Release in User Story Mapping), so a reader who knows the method recognizes it.
- **The rule is enforced.** A lint rule forbids Japanese characters in string and template literals outside the dictionaries (tests and comments aside), so new text cannot bypass them.

## Consequences

- A page without `lang` now renders the kit's UI in English. Existing Japanese pages need `lang="ja"` (on `<html>` or the template element) to keep their UI; the docs and the agent skill say to write it. This is a breaking change, taken while the package is still in beta.
- Base data and author attributes (a diagram's `heading`, a question's text) are the author's content and are never translated; only text the kit renders itself is.
- A reader's pick applies to every template page of the origin, including pages written in the language they picked; a page-local pick would have to be repeated on every generated page.
- Elements outside a template do not get a select; they follow a pick only when they sit inside the template that received it.
- Every entry carries both dictionaries. That is a few kB per entry, and a new language adds to every page.
- A new language is a new dictionary in every module; the types make a missing key a compile error rather than a blank label.
- Right-to-left layout and plural rules are out of scope. Adding a language that needs them would require revisiting the dictionary helper.
- Tests compare text through the dictionaries instead of literals, so a wording change does not churn tests.
